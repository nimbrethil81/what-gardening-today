# Configuration items — What Gardening Today?

A living register of values and design choices that are currently fixed in code or
in the Supabase dashboard, but that we might reasonably want to revisit later. The
point is so that when a number or a behaviour needs changing, we know *what* it is,
*where* it lives, and *why* it was set the way it was — without re-deriving it.

This file is a convenience index, **not** an authoritative spec. `SPEC.md` remains
the source of truth for architecture and schema; this just gathers the dials in one
place. It is expected to grow as v2 is built out.

_Last updated: 2.12 — multiple gardens per user._

---

## Product / behaviour settings

| # | Item | Current setting | Where it lives | Why / trade-off |
|---|------|-----------------|----------------|-----------------|
| 1 | Weather cache freshness | 30 minutes | `today` Edge Function — `CACHE_TTL_MINUTES` | How long a weather reading is reused before a fresh call. Longer = fewer API calls, but the widget and the task filtering go staler. Not near any API limit today, so 30 min favours freshness. |
| 2 | Weather cache location grouping | ~0.1° (≈11 km), i.e. 1 decimal place | `today` Edge Function — `COORD_ROUNDING_DP` | How coarsely nearby gardens share one weather fetch. Finer = more per-spot accuracy, more calls; coarser = fewer calls, neighbours may share slightly-off weather. Weather rules are coarse, so 0.1° is ample. |
| 3 | Sign-in method | Google OAuth (primary); emailed 6-digit code (dormant fallback) | Supabase Auth → Providers (Google); email flow behind the sign-in screen's "Use email instead" link | Google is the free, viable social provider, and app-initiated OAuth returns cleanly into an installed iOS PWA (magic links don't). The email code path is kept but parked until custom email is set up for friend invites. |
| 3a | Access / invite control | Invite-only | Supabase: public sign-ups OFF + the Users list; frontend `shouldCreateUser: false` | An account exists only once its email is added in the dashboard. Applies to every method — a Google sign-in from an un-added email is refused (`signup_disabled`). Turning sign-ups on would make the app open to anyone (each getting their own garden). |
| 4 | "Email not invited" message | Friendly / specific ("not on the guest list") | Sign-in screen copy | Clear for a small circle of known friends. The neutral alternative gives away less about who has an account. |
| 5 | Location entry — primary method | Postcode (via postcodes.io); "use my current location" offered as the secondary option | Garden form (first run / add another / edit) | Postcode always works with no permission prompt. Either method is plenty precise given the 0.1° weather rounding. |
| 6 | Location confirmation | On — shows e.g. "📍 Amersham, Buckinghamshire" after a location resolves | Garden form (first run / add another / edit) | Reassures the user the location landed on the right area before they commit. |
| 7 | Inventory grouping source | `garden_item.legacy_category` (the tile the item was added under) | Frontend inventory read; also written on every new add | Keeps grouping identical to today for migrated items, and uniform for new ones. NB this reads a column the Stage 1 schema comments as "never read by v2" — a conscious repurposing to record in the SPEC rewrite. |
| 8 | Garden timezone | `Europe/London`, and **not editable** | `create_garden` default; `garden.timezone` | The app is UK-only. Note the asymmetry introduced in 2.12: a garden's *location* can now be corrected, but its timezone cannot. `garden.timezone` drives every piece of date arithmetic (`select_tasks` cooldown, `record_garden_day`), so moving a garden abroad is not a postcode change — it would need the timezone to move with it, and the two would have to stay consistent. |
| 9 | Post-write refresh model | Re-fetch the affected view after each write (complete / hide / add / remove) | Frontend | Screen always reflects the true database state; avoids UI/DB drift. Optimistic instant-updates could be layered on later for extra snappiness. |
| 15 | Activity recording | On — one row per garden per day, with a count of opens | `garden_day` table; written by `today` via `record_garden_day()` | Answers the one question that cannot be asked retrospectively: do people come back? `task_completion` shows what a garden *did*; this shows that somebody *looked*, and an open producing no completion is the churn signal. Deliberately the coarsest record that answers it — no times of day, no which-tasks-were-shown, nothing about the user. Turning it off means never being able to reconstruct the gap. |
| 16 | Activity retention | Unlimited — nothing is pruned | `garden_day` | Bounded at 365 rows per garden per year (~100 bytes each), so a thousand active gardens is ~20 MB/year against a 500 MB free tier, and it adds nothing to MAU billing. If it ever mattered, rows older than ~2 years would collapse into a monthly summary; that job is described in a comment in `db/10_activity.sql` and deliberately not built. |
| 17 | Inventory ceiling | 200 active items per garden | `garden_item_guard()` — `v_max_items`, enforced by a `BEFORE INSERT` trigger | **Not a paywall, and must not become one.** A cap that binds pushes users to leave things *out* of their inventory to stay under it, and the app is then advising on a garden it can no longer see properly — degrading recommendations to sell a subscription. This is an abuse/performance guard: inventory is the one user-controlled input to `select_tasks`, which walks every active item on every open. A mature garden plus an allotment might reach 80. Invisible in the UI until somebody approaches it; removed (soft-deleted) items don't count. Raising it costs query time on the largest gardens; lowering it would start binding on real ones. |
| 18 | Entitlement state | Dormant — no products, no entitlements, every blueprint core | `product` / `pack_member` / `entitlement` tables | Installed empty so nothing is retrofitted later. Entitlement sits on the **user**, not the garden (one person tending two gardens bought one thing). The governing rule is that entitlement grants the right to **add**, not the right to **see**: anything already in a garden stays visible to every member forever. A blueprint in no *live* pack is core, so retiring a pack releases its contents rather than stranding them. Prices are not held here — the stores are the merchants of record. |
| 19 | Account deletion | Immediate and irreversible; two-tap confirmation | `delete_my_account()`; settings panel in `index.html` / `app.js` | No grace period, for a project-specific reason: a deferred deletion needs something to run a month later and finish the job, and the only scheduler here is a twice-weekly GitHub Action already observed to stop silently. A deletion that quietly never happens is worse than none. Gardens the user was last member of are deleted; a garden where they were the only owner is handed to the **longest-standing remaining member** (ties broken by user id, so the outcome is deterministic). Two taps rather than type-to-confirm: chosen for friction balance, and revisitable — there are no backups, so this is the only thing standing between a mis-tap and permanent loss. |
| 22 | Default garden on open | The one you were last in; falls back to your oldest (`created_at` ascending) | `app.js` — `LAST_GARDEN_KEY` (`wgt.lastGarden` in browser localStorage), keyed by user id | Matches how the feature is used: mostly your own garden, occasionally somebody else's, so the app should stay where you left it. Keyed by user id so two people sharing a tablet don't inherit each other's. Validated on every open against the gardens you can actually see — a deleted garden, a removed membership or a leftover from another account falls back silently rather than erroring. **Per device, not per account**: switching on a phone does not move a tablet. Storing it server-side would mean a write on every switch to save a tap. Degrades safely: with storage blocked you always get your oldest. Alternatives were "always the oldest" (predictable, but wrong every morning for the secondary garden) and asking each time (a tap for nothing). |
| 23 | Garden switcher ordering | Oldest first, by `created_at` | `app.js` — `loadGardens()` | Stable. Alphabetical reshuffles the list every time a garden is renamed, which is exactly when the user is least expecting the order to move. |
| 24 | Garden ceiling | 10 gardens per user, counted over **membership** not ownership | `create_garden()` — `v_max_gardens` | **Not a paywall**, same as #17. Nothing bounded garden count before 2.12 because nothing offered a second one; a button that creates rows needs a limit somewhere. Ten is far above honest use — the driving case is two, a keen allotmenteer might reach five — and invisible until somebody is doing something absurd. Counted over membership so it cannot be walked around once sharing exists. Raising it costs nothing much; the real cost of many gardens is per-garden query work at open time, which is already bounded by #17. |
| 25 | Deleting a shared garden | Refused while any other member remains | `delete_garden()` | The alternative — allow it with a confirmation naming who loses access — was considered and rejected for now. A non-owner has no notification channel: they would open the app one morning to find years of their own history gone, erased by a tap they never saw. Refusing makes destroying somebody else's data require an explicit act against that person (remove them, then delete) rather than one tap aimed at something you think of as "mine". Deliberately stricter than account deletion, which hands shared gardens on. Loosening it later is a one-line change plus a confirmation panel. |
| 26 | Deleting your last garden | Allowed — you end up with none, and land on the setup screen | `delete_garden()` (deliberately unchecked); `route()` in `app.js` | Zero gardens is already a real, handled state: it is where every new user starts. Blocking it would build a trap whose only exit was deleting the whole account, which is far more destructive than what was asked for. |
| 27 | Duplicate garden names | Allowed, with a non-blocking warning on the form | `app.js` — `validateSetup()` | Two gardens called "Home" are genuinely hard to tell apart in the switcher, so say so before it happens. Not enforced, because the name lives on the `garden` row, which can be shared between users — "unique per user" is not a rule the database can express. Names are capped at 40 characters and truncate with an ellipsis in the header. |

## Operational / platform notes

| # | Item | Current setting | Where it lives | Why / trade-off |
|---|------|-----------------|----------------|-----------------|
| 10 | Free-tier keep-alive | Implemented: twice-weekly ping (Mon & Thu) | GitHub Action `keepalive.yml` → `keepalive()` RPC | Supabase free-tier projects pause after ~7 days with no database activity; Mon/Thu keeps the longest gap at 4 days. Change the `cron` line in the workflow to adjust cadence. |
| 11 | Service-worker cache version | `CACHE_NAME` string in `sw.js` | `sw.js` | Must be bumped on any deploy that changes a cached file, or installed PWAs won't pick up the update. |
| 12 | Allowed browser origins (function) | `https://nimbrethil81.github.io` (+ localhost for testing) | `today` Edge Function — `ALLOWED_ORIGINS` | The origins permitted to call the function. Add an entry if the app is ever served from another address. |
| 13 | OpenWeather endpoint | 2.5 "current weather", metric units | `today` Edge Function | Matches the proven 1.x call. OpenWeather has been steering new usage toward newer endpoints; worth a check if the key is ever re-issued on a new plan. |
| 14 | Supabase env-var names (function) | Legacy `SUPABASE_URL` / `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` (auto-provided) | `today` Edge Function | These legacy names are slated to deprecate at the end of 2026 in favour of the publishable/secret-key scheme — a small future swap. |
| 20 | Database backups | None — free tier has no automated backups | Supabase plan | Curated content is safe regardless: it regenerates from the workbook via the publish pipeline, which is a genuine architectural strength. **User data is not** — gardens, inventories and completion history have no restore path, and account deletion is irreversible. The strongest argument for revisiting the paid tier before the app opens to strangers rather than before it opens to friends. |
| 21 | Deletion cascade dependency | Every table referencing `auth.users` or `garden` must declare `ON DELETE CASCADE` (or `SET NULL`) | Schema-wide; audited by the readout at the foot of `db/12_account_deletion.sql` | Account deletion works only while this holds. A future table that forgets would make deletion fail with an obscure constraint error at the worst possible moment — the one moment a user is least inclined to be patient. Re-run that readout after any schema change; every row should read `ok`. |
